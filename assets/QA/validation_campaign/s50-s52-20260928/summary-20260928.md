## S50 scenarios and observations

1. The official `start_on_windows.ps1 -Action Launch` started the current
   source FastAPI/Node stack against the disposable resource root. `/api/health`
   returned HTTP 200.
2. The database-backed setting `global.seed=20260928` and synthetic persisted
   report `s50_validation_20260928` were seeded. API readback returned the
   setting, report request ID, `s50-synthetic.png`, `synthetic:s50`, and
   `s50-revision`. The in-app browser rendered the same seed on Settings and
   the same one-session report card on Reports.
3. `KillProcesses` stopped the full launcher-owned tree. No `LISTENING` entry
   remained on ports 5003 or 8003. After WAL checkpointing, the preserved
   backup SHA-256 was
   `0c98d823e065f1f7ee0f1a2fad182ca8025e8126ad368837d38202b647032a60`.
4. Relaunch returned HTTP 200, the setting and report survived API readback,
   the rendered Settings/Reports surfaces showed them again, and
   `PRAGMA integrity_check` returned `ok`.
5. With services stopped, deterministic schema drift was injected by adding
   `datasets.s50_unexpected TEXT`. The database remained structurally readable
   (`integrity_check=ok`) but the backend failed closed at startup. Its
   sanitized evidence records that the database was at Alembic head but
   differed from the current ORM schema; no credential or user content was
   exposed.
6. The frontend stayed available while health failed. The rendered startup
   state showed `XREPORT could not reach the local backend service` and a
   `Retry connection` button. Clicking Retry returned the state to
   `Preparing XREPORT` while the backend remained unavailable.
7. The corrupted database remained unchanged at SHA-256
   `41007a103182f01378ea4ae69e24a1467e45e71e4ac71da99ad1c4bf315a09b8`,
   159744 bytes, with `s50_unexpected` still present; it was not silently
   recreated. The backup remained distinct at the hash above.
8. Restoring the backup produced matching current/backup hashes, removed the
   injected column, returned `integrity_check=ok`, and restored HTTP 200 plus
   the same setting/report API and rendered readback. The disposable root was
   then removed.
