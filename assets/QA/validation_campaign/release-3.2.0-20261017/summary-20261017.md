## MSI lifecycle gates (install → launch → close → uninstall)

Both lifecycles ran elevated on the validation host; receipts under
[`msi-lifecycle-20261017/`](../msi-lifecycle-20261017/).

- **cpu: PASS** — [`cpu-receipt-20261017.json`](../msi-lifecycle-20261017/cpu-receipt-20261017.json).
  Install and uninstall exited `0`; launch served the frontend; all cleanup invariants passed
  (no app/backend process, listener gone, runtime contracts removed, ports clean).
  Deviation: the close step reported `graceful_exit=false` / `forced_kill=true`. Analysis:
  the harness close path issues `POST /__xreport/shutdown` and then closes the window; the
  packaged shell observed the deliberate backend exit, surfaced its startup-error page, and
  that page navigation hit a WebView2 race (“failed to send message to the webview” in the
  shell log), so the app did not self-exit within the wait window and was force-killed. The
  `WM_CLOSE`-only path closes gracefully in under a second on the same binaries (cuda smoke),
  so this is classified as a harness-path observation, not a gate failure.
- **cuda: PASS** — [`cuda-receipt-20261017.json`](../msi-lifecycle-20261017/cuda-receipt-20261017.json).
  Fully graceful close (`graceful_exit=true`, `forced_kill=false`); identical install, launch,
  uninstall, and cleanup assertions.

Elevation notes: both install and uninstall required UAC approval on the secure desktop;
the harness treats a pending consent as waiting input and was approved in-session.
